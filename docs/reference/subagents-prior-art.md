### Buzz

- **A thread is a session.** `buzz-acp` derives one ACP session per thread by default
  (`crates/buzz-acp/src/scope.rs`): a top-level mention opens a session rooted at that message, and a reply in
  the thread reuses it. A DM stays one session. The agent's prompt tells it that it is "one session of your
  agent identity — not the only copy" (`session_model_thread.md`). This is the opposite direction to ours: a
  person opens a thread and an agent session follows it, where ours has the agent open a thread for each
  subagent.
- **Activity stays behind the answer.** Channels see the agent's reply and typing dots; **View activity** on
  the reply shows the rest (`docs/buzz-help.md` in `buzz-app`). Subagents are lines in that activity
  (`src/features/agents/local-activity.ts`).
- **Goose children are registered with the parent.** `src/bundled/goose/forward-children.ts` registers a
  child session only from a live `delegate` call, because Goose strips `subagentSessionId` from every other
  tool's result (its comment cites goose 1.57.0).

### Slack and Discord, for threads

- **Slack.** Threads hang from a message, with "Also send to channel" to copy a reply into the main view. In
  a one-to-one DM a person is notified of every thread reply; in a channel only if they started it, replied or
  were mentioned. Home → Threads lists followed threads, unread first. Agents now live in the Messages tab as
  DMs that answer in threads (`agent_view`, changelog of 2026-06-30). Streamed task cards cap at 50 per message
  and a stream lasts at most 10 minutes; on timeout open tasks become `error`.
- **Discord.** Public threads are visible to everyone who sees the channel; private ones by invite. Members are
  tracked per thread. A `THREAD_CREATED` system message appears in the channel only for a thread started from
  an older message. The Threads FAQ page refused the fetcher (HTTP 403), so the user-facing details were read
  from the developer documentation only.

## MLS subgroup branching

From [RFC 9420](https://www.rfc-editor.org/rfc/rfc9420.html), sections 3.4, 8.4, 8.6, 11.2, 11.3 and 12.4.

**What it is.** "A new group can be formed from a subset of an existing group's members, using the same
parameters as the old group" (11.3). One member:

1. fetches "a new KeyPackage for each group member that should be included in the subgroup";
2. creates the new group with an initial Commit holding a PreSharedKey proposal of type `resumption`, usage
   `branch`, taken from an epoch of the old group;
3. sends the Welcome to the subgroup's members. The new group starts at epoch 1.

The PSK proves that the members "were members of the group during the epoch from which the resumption key was
extracted" (3.4). Each leaf in the subgroup "MUST match some LeafNode in the original group". Version and cipher
suite are the old group's.

**After that the two groups are independent.** "Groups and epochs are generally independent of one another",
and branching has no effect on the original group (3.4). Adding someone to the branch later is an ordinary Add
with a fresh KeyPackage; the RFC requires neither membership of the parent nor the PSK for it.

**What one would cost in Marmot** (inferred from how Marmot groups work):

- a fresh KeyPackage from every member's every device, each used once, and a Welcome to each;
- a new Marmot group in full: its own group data (name, relays, admins), its own subscriptions, its own commits
  and epochs from then on;
- for each later joiner of the main chat, a separate Add to every branch they should see.

**What exists.** OpenMLS at MDK's pinned revision implements it (`MlsGroup::branch_info`,
`MlsGroupBuilder::branch`, `StagedWelcome::build_from_branch`; the docs warn that `BranchInfo` carries the
parent's resumption secret). MDK does not use it: no branch PSK appears outside OpenMLS's storage of resumption
secrets. The Marmot specification's "branch" means a fork candidate during convergence, not RFC 9420
branching.

**For subagent threads it does not fit** (inferred). A subagent's thread has the same members as the chat, so
the one thing a branch proves adds nothing. Its cost is paid per subagent, and subagents often live for seconds.
The chat would scatter across groups, and an app would need a group-inside-a-group view.

**For a private side channel** ([Q-11](../open-questions.md#q-11-what-keeps-sensitive-output-from-spreading)),
noted and not designed: a branch holding only the owner's devices and the agent would be a two-party group
whose creation proves both were in the main chat at that epoch. A plain new group between them gives the same
privacy; what a branch adds is a cryptographic link to its parent, which an app could show as "private to you,
from this chat". It would still cost KeyPackages and Welcomes once, not per subagent.

## What Marmot has

### MDK at `6f6b427`

- **Thread messages are NIP-22 comments.** `send_thread_message` builds kind 1111 with `E`/`K`/`P` for the
  root and `e`/`k` for the parent (`crates/marmot-app/src/messages/intents.rs`). MDK leaves out NIP-22's
  parent-author `p`, because on Marmot a `p` is a mention. The contract is
  `docs/marmot-architecture/overview/thread-messages.md`.
- **Placement follows the parent.** A parent outside any thread becomes the root; a parent inside a thread passes
  its root on, so a thread started on a thread message stays under the same root
  (`crates/marmot-app/src/client/thread_placement.rs`). A root the device no longer holds keeps the kind and
  author its nearest descendant names.
- **Only some kinds can be in a thread.** A row gets a `thread` field when it is a kind 1111 comment, or a kind
  9 chat message or kind 1068 poll that joins a thread by naming its root with `E`
  (`crates/storage-sqlite/src/app/timeline/threads.rs`, `own_thread`). **A kind 1201 agent item is never placed
  in a thread today**, whatever tags it carries.
- **An agent item may not carry `e`**: MDK keeps it for the target of an edit (`AGENT_REQUEST_ITEM_TAG` in
  `crates/traits/src/agent_events.rs`). No check against `E`, `K` or `P` was found, so they would pass
  (inferred).
- **Comments alert like chat.** "A thread message notifies like chat" (`notification_traffic` in
  `crates/marmot-app/src/notifications.rs`), and counts toward unread, previews and push. Only kind 9 has the
  silent `phase` exception (D-078).
- **Full threads are not built.** Thread summaries, paged descendants and per-thread read state are
  [MDK issue 2787](https://github.com/marmot-protocol/mdk/issues/2787), open. [MDK issue
  1318](https://github.com/marmot-protocol/mdk/issues/1318), open, proposes "conversation lanes" so one agent
  chat can hold several sessions, citing Telegram topics and Discord threads.

### White Noise apps

- **Linux** has Discord-style threads: a stack of thread views, each filtering the one timeline by thread, and
  threads nest to any depth (`app/threads.odin`, read 2026-11-23). Whether it opens a thread under a kind 1201
  row was not checked.
- **iOS, macOS and Android** have no thread view. MDK's contract says they show every thread message "inline in
  the main timeline with a one-level quote of its parent".
- **Android plans an optional one**: [whitenoise-android issue
  2841](https://github.com/marmot-protocol/whitenoise-android/issues/2841), open, a per-channel switch "View
  replies in threads", off by default, with reply counts, a thread pane and a catch-up action. No iOS issue for
  threads was found.

## What follows for the design

1. **Everyone who shows subagents shows a running list near the composer, and opens a subagent beside or over
   the parent.** Claude Code's panel, Codex's `/subagents`, the Codex IDE's active list, T3 Code's Agents list
   and Working section. None shows a subagent's activity in the main conversation.
2. **Approvals surface where the person is, naming the subagent.** Claude Code, Codex and T3 Code all do. Nobody
   makes the person open the thread to find it.
3. **Talking to a subagent is the exception.** Only Claude Code's terminal and OpenClaw let a person type to a
   running one; T3 Code makes agent-started subagents read-only on purpose. Elsewhere it goes through the parent.
4. **Stop on the parent stops the tree** in T3 Code, OpenClaw and Hermes's `/stop`. Claude Code has no stop-all,
   and Codex's interrupt of the parent leaves subagents running.
5. **Finished ones fold away; nobody deletes them sooner.** Claude Code removes rows after 30 s but keeps
   `/tasks`; Discord archives but keeps.
6. **Four of eight harnesses link child to parent in their events** (Codex, Claude Code, OpenCode, and OpenClaw
   by session key). The others give a line of text or nothing.
